# 项目约定模板（Project Conventions Template）

生成最终文档时使用这个结构。把所有 `[方括号]` 占位符替换成对话中**实际提取到**的内容；
没提取到的非必填项直接删掉那一行，不要编。

---

```markdown
**项目定位**

[项目名] —— [一句话说明它在做什么、为谁做]。当前阶段：[阶段]。

**技术约定**

- 技术栈：[语言 / 框架 / 关键依赖]
- 固定命令：构建 `[命令]`、测试 `[命令]`、运行 `[命令]`
- 目录与命名：[约定]

**协作方式**

- 自主程度：[哪些事可以直接做，哪些必须先问]
- 反驳：[允许 / 不允许 / 在什么条件下允许]
- 沟通：[简洁还是详尽；语言；是否需要解释「为什么」而不只是「做了什么」]

**验证要求**

- 完成标准：[跑什么命令、看什么证据才算做完]
- 禁止：[例如「不得用 agent 自己的总结当证据」]

**边界与底线**

- 绝不能碰：[生产数据 / 密钥 / 某目录 / 某分支 ……]
- 失败处理：[静默修复 / 立即上报 / 记录后继续]

**长期方向**

[项目要往哪走，什么算成功]

**已踩过的坑**

_（记录重复踩过的坑，避免重犯。）_
```

---

## 模板规则

1. **「已踩过的坑」是固定空段。** 永远保留为空占位，它靠后续对话逐步填充，不在引导阶段写内容。
2. **「项目定位」是一段话。** 紧凑，不换行。
3. **协作方式是行为规则，不是形容词。** 每条都写成可执行的祈使句 ——
   写「改完必须跑 `pnpm build` 验证」，而不是「要严谨细致」。
4. **固定命令原样照抄。** 用户说的 `./.venv/Scripts/python.exe` 就写这个，不要"美化"成 `python`。
5. **总长度 400 字以内。** 密度优先于篇幅，每个字都要站得住。
6. **语言跟随用户在 Phase 1 选定的语言。** 不要强制英文。
7. **不确定就标出来。** 如果是推断而非用户明说的，写成「（推断）…」并在确认时主动指出。
